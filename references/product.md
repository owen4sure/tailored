# 產品事實與訪談：PRODUCT.md

**先確認產品事實，再定視覺方向，最後才動手。** 連產品在解決什麼問題都沒搞清楚，挑配色和字體就沒有意義，「量身打造」也無從判斷。

---

## 誰負責什麼

| 未知的事 | 誰處理 | 例子 |
|---|---|---|
| 查得到的事實 | 自己查：程式碼、既有畫面、文件、資料表 | 有哪些角色、真實欄位、狀態與權限 |
| 使用者的目的與限制 | 問使用者 | 誰會用、最想完成什麼、有什麼絕對不能出現 |
| 視覺偏好 | **不用問答問，用看的選**（見 directions.md） | 配色、字體、外框、密度 |
| 暫時查不到的 | 記下缺口與影響，先做不依賴它的部分 | 還沒拿到的真實資料 |

不要要求不熟技術的使用者說明欄位對應或後端怎麼做；也不要問「想要高級還是簡約」「直覺還是專業」，這些答不出可以用的決定。

## 訪談原則

1. **能推斷的不問。** 先讀 README、既有頁面、程式碼、文件，把推斷寫成草稿請使用者確認。
2. **問得準。** 一輪最多 5 題，每題附背景與建議答案，讓使用者可以只回「照建議」。依賴其他答案的題目放到下一輪。
3. **「沒有的功能」跟「有的功能」一樣重要。** AI 很容易暗示產品有它其實沒有的能力。
4. **數據一定要有出處。** 頁面上的數字、評價、客戶名，只能來自 PRODUCT.md 的「可證實的數據」。
5. **答過的不重問。** 新答案和舊紀錄衝突時，以新的為準並更新 PRODUCT.md。

## 問題庫（依缺口挑，不必全問）

| 主題 | 問題 | 為什麼要問 |
|---|---|---|
| 一句話 | 這個產品幫誰解決什麼問題？ | 標題與首屏的來源 |
| 使用者 | 誰會用？在什麼情境、什麼裝置？當下是什麼狀態（趕時間、第一次用、每天用）？ | 決定語氣與密度 |
| 首要任務 | 打開這個畫面，最想完成的一件事是什麼？ | 決定主角與唯一的主按鈕 |
| 功能 | 現在有哪些功能？哪個最重要？哪些還沒有？ | 決定誰佔最大面積，避免暗示不存在的能力 |
| 證據 | 有哪些真實數據、客戶、畫面可以用？ | 唯一合法的數據來源 |
| 禁區 | 有哪些設計、語氣、元素絕對不能出現？ | 品牌、法規、過去的教訓 |
| 品牌 | 有沒有必須沿用的 logo、色彩、字體、元件庫？ | 例如公司設計系統 |
| 參考 | 有沒有喜歡的產品或畫面？喜歡它的哪個部分？ | 只記錄喜歡的具體特徵，不照抄 |
| 成功 | 做完之後，怎樣算好用？使用者自己會怎麼試？ | 驗收標準 |

內部工具、後台的輕量模式只需要：一句話、使用者與情境、首要任務、有與沒有的功能、禁區。

## 什麼時候算問完

寫得出 PRODUCT.md，而且使用者看過、回「對」或修正完。還沒確認前，不要開始做依賴這些答案的部分；可以先做不依賴答案的研究。

## PRODUCT.md 模板

寫在專案根目錄。之後所有設計與程式都以它為準。

```markdown
# PRODUCT.md

## 一句話
<產品幫誰解決什麼問題>

## 使用者與情境
- 誰：<身分、熟悉程度>
- 在哪裡用：<裝置、場合>
- 當下狀態：<趕時間、第一次用、每天用…>

## 首要任務與首要訊息
- 首要任務：<使用者來這裡要完成的一件事>
- 首要訊息：<三秒內必須讀到的一句話>

## 有的功能（可以展示）
- <功能>：<一句說明>（★ 標記最重要的一項）

## 沒有的功能（不准暗示有）
- <…>

## 可證實的數據與背書（只有這裡列的能上頁面）
- <數字或客戶名>｜出處：<連結或文件>

## 禁區
- <不能用的設計、語氣、元素，以及原因>

## 既有品牌資產
- <必須沿用的 logo、色、字、元件庫；沒有就寫「無」>

## 成功的樣子
- <使用者用完會做什麼、怎麼算好用>
```

PRODUCT.md 寫好之後，詢問使用者要不要在專案的 AGENTS.md 或 CLAUDE.md 加一段：「任何介面改動前先讀 PRODUCT.md 與 DESIGN.md，改完用 tailored 審查。」
