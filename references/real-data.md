# 真實功能與資料

好看但不能用、或用了會弄壞資料的畫面，比醜的畫面更糟。改既有系統、或要接上真實資料時，照這份做。

---

## 先查清楚真實的樣子

- 每個要出現在畫面上的功能，查出：實際入口、可操作的角色、主要欄位、資料來源、狀態、下一步會流向哪裡。
- 把核心路徑寫成一行：`角色 → 入口 → 查找或新增 → 輸入 → 驗證 → 儲存 → 下一步 → 返回`。設計要讓這條路順，而不是只讓首頁好看。
- 查不到或沒有權限查的部分，列為缺口，不用假功能補位。

## 不能造假

- 不編造功能、數字、客戶、評價、通知或成功狀態。只能用 PRODUCT.md「可證實的數據」裡的。
- 原型可以用示例資料，但要標示「示例」，而且示例要像真的（真實長度、真實格式），不要用完美的整數。
- 真的儲存或送出成功之後才顯示成功；不用前端動畫或本機儲存冒充後端完成。

## 改名與翻譯只改顯示

- 只改使用者看到的文字；欄位代碼、選項的原始值、關聯目標、介面參數一律不動。
- 優先用系統原生的翻譯機制，不用整頁文字替換，不改使用者的資料。
- 驗證方式：改動前後欄位代碼、選項值、關聯目標相同；存一筆測試資料再讀回，確認後續帶入和轉單仍然正確。

## 試用與權限

- 使用者想免登入體驗時，先確認是展示原型還是授權的隔離試用。不關掉真實系統的驗證、不提升權限、不把管理員密碼放進前端。
- 測試資料不能污染正式資料；需要寫入時，用測試環境或測試副本。

## 跨裝置

- 跨裝置「已處理」的狀態要存在伺服器，不靠單一裝置的本機儲存。
- 分清楚「讀過通知」和「處理完工作」，不要讀了通知就清掉待辦。
