# 審查程序、子代理提示詞、review.json 格式

審查分兩層，**每一回合都整頁重審**，不是只檢查上一回合修過的地方，因為修正常常引入新問題。

- **第一層：做對了嗎。** 四原則打分，加上三項測試，回扣 PRODUCT.md 的承諾。
- **第二層：有沒有犯已知的錯。** 拿 antipatterns.md 逐條掃，並逐條處理 scan.json 的每一筆命中。

---

## 為什麼要獨立審查

設計的人會用「我本來的意思是…」替畫面辯護。使用者看不到你的意圖，只看得到畫面。
所以審查者只根據**截圖、產品事實、規則**判斷；畫面上看不出來的意圖，等於不存在。

**有 Agent 工具時**：每一回合開一個全新的子代理當審查者（不要沿用上一回合的子代理，避免被自己上回的判斷綁住）。
**沒有子代理時**：自己審，但只看截圖與 PRODUCT.md，先寫完 findings 再回頭看程式碼定位；review.json 的 reviewer 填 self，報告會註明「非獨立」。

---

## 子代理提示詞模板

平常不用手填：`python3 <skill>/scripts/loop.py brief design-review` 會產生路徑全部填好的版本（也存成 round-N/brief.md），內容跟下面相同，還會附上上一回合的審查、修正紀錄與下一個可用的 F 編號。
沒辦法跑腳本時，才把 `<…>` 換成實際路徑後整段交給子代理：

```text
你是獨立的設計審查者，沒有參與這個設計。只審查，不要修改任何檔案（review.json 除外）。

請依序讀：
1. 產品事實：<專案>/PRODUCT.md；視覺契約：<專案>/DESIGN.md（若有）
2. 規則：<skill>/references/principles.md、<skill>/references/antipatterns.md、<skill>/references/review-rubric.md；
   品味基準：<skill>/references/craft.md，以及符合這次畫面類型的 <skill>/references/platforms.md 段落
3. 本回合掃描結果：<round>/scan.json
4. 截圖：<round>/desktop-1440-fold.png、desktop-1440-full.png、mobile-390-fold.png、mobile-390-full.png
5. 上一回合審查（若有）：<上一回合>/review.json，同一個問題沿用同一個 F 編號
6. 程式碼只用來定位問題、寫出精確的修改位置，不要用來推測設計意圖：<原始碼路徑>

要做的事：
A. 第一層：依 principles.md 給四原則打 0 到 3 分並寫理由；執行三秒測試、換名測試、核心任務測試。
B. 第二層：逐條處理 scan.json 的每一筆命中，確認就放進某個 finding 的 scan_ids，誤報就寫進 dismissed 並說明理由；
   再對照 antipatterns.md 中標「人工」的規則與四原則，補上機器抓不到的問題。
C. 每個 finding 都要寫出能直接動手的改法（改哪個元素、改成什麼），優先考慮「刪除」。
   fix 只寫對畫面的具體改法，不要寫「先回到步驟 2」這類流程指令；方向有問題就照實打分、寫 D5 或「原則」finding。
D. 列出 positives：做對的地方，避免修正時被破壞。
E. 依本檔格式寫入 <round>/review.json，然後回報：預估閘門結果、P0／P1 數量、最關鍵的三個問題。

文字規範：中文用全形標點，不用破折號；選擇器、檔名、程式碼用反引號包起來。
```

## 三項測試

| 測試 | 怎麼做 | 通過條件 |
|---|---|---|
| three_second 三秒測試 | 看桌機與手機的首屏截圖，寫下「這頁在說什麼」與「我該按哪裡」 | 兩者都跟 PRODUCT.md 的首要訊息與首要任務一致 |
| name_swap 換名測試 | 把產品名換成同類競品名，逐段讀首屏與主要功能區 | 兩個區塊各至少有一個元素對競品來說是錯的或沒意義（獨特機制、具體情境、真實數據） |
| core_task 核心任務測試 | 從首要任務出發，在截圖上找完成路徑 | 入口在首屏或一次捲動內、標示清楚、不被裝飾干擾，手機上也點得到 |

note 欄要寫**看到了什麼**，不是只寫「通過」。

## review.json 格式（v1）

```json
{
  "round": 2,
  "reviewer": "subagent",
  "scores": {
    "符合預期": {"score": 2, "note": "主按鈕都有真實目的地；狀態燈仍是裝飾"},
    "主次分明": {"score": 1, "note": "首屏三顆實心按鈕搶主角"},
    "克制": {"score": 2, "note": "…"},
    "量身打造": {"score": 1, "note": "…"}
  },
  "tests": {
    "three_second": {"pass": true, "note": "三秒讀到：網站掛了會打電話；該按「加入第一個網址」"},
    "name_swap": {"pass": false, "note": "首屏標題換成任何監控服務都成立"},
    "core_task": {"pass": true, "note": "主按鈕在首屏左側，手機也在第一屏"}
  },
  "findings": [
    {
      "id": "F01",
      "rule": "A1",
      "principle": "符合預期",
      "severity": "P1",
      "title": "標題上方的膠囊看起來能點",
      "location": "首屏主標題正上方，`header.hero > div.badge`",
      "problem": "有框、有底色、圓角膠囊，外觀像按鈕，點了沒有反應",
      "why": "使用者會試著點它，失敗之後開始不信任畫面上的其他按鈕",
      "fix": "刪除 `div.badge`；「AI 告警」這個資訊併進副標的第一句",
      "scan_ids": ["S01"]
    }
  ],
  "dismissed": [
    {"scan_id": "S07", "reason": "價格方案本來就該等價比較，DESIGN.md 已允許"}
  ],
  "positives": ["主控台告警演示直接展示產品機制，保留"]
}
```

欄位規則（gate 會檢查）：

- `scores`：四原則都要有，0 到 3 的整數；低於 3 分要寫 note。
- `tests`：三項都要有 `pass`（true／false）與 `note`。
- `findings`：沒有問題也要給空陣列。每筆都要有 `id`（F01 格式，跨回合沿用）、`rule`（規則編號，清單外填「原則」）、`principle`、`severity`、`location`、`problem`、`fix`。P0／P1 的 fix 要具體。
- `scan_ids`：這個 finding 對應哪些掃描命中。
- `dismissed`：排除的掃描命中，每筆都要有理由。**scan.json 每一筆命中都必須出現在 scan_ids 或 dismissed，少一筆閘門就判「審查不完整」。**
- `waiver`：只有使用者能豁免 P0／P1，格式 `{"by": "user", "reason": "…"}`；審查者或設計者不能自行豁免。
- `positives`：可選，但強烈建議寫。

## 編號延續

- 同一個問題跨回合沿用同一個 F 編號，閘門才能判斷「已解決、仍存在、新出現、回歸」。
- 新問題接續最大號（上一回合到 F07，新的從 F08 開始）。
- 上一回合 fix 明確要求、修正者也照做了的改法，除非違反原則，否則不要列成新問題。真的要推翻時，**沿用原本那個 F 編號**，並在 why 說明為什麼要改回；這樣閘門才看得出來回打轉。
- 修好又回來的問題叫**回歸**；同一個擋閘門的問題回歸兩次，閘門會停下交給使用者，因為那代表修正在兩個壞狀態之間打轉。
- 審查時一併讀上一回合的 `fixes.md`（修正者寫的每個 F 改了什麼），核對修正是否真的落實在畫面上。

## 實際操作驗證（閘門之外，交付前一定要做）

閘門判斷的是設計有沒有違反原則；畫面能不能用，要另外實際操作。

1. 用真的瀏覽器走一遍核心任務：找到入口、完成、返回。手機產品在手機寬度走一次。
2. 有接真實資料的，存一筆測試資料再讀回，確認欄位、關聯與下一步都正確（見 `real-data.md`）。
3. 比較頁或多個方向時，每一個都打開操作，不只測自己最後改的那個。
4. 照 `checklist.md` 逐項確認，做不到的寫「未驗證」並說明原因。

交付說明分開寫：閘門結果、實際操作驗證了什麼、沒驗證什麼、使用者的視覺選擇是否已確認。閘門通過不等於使用者滿意，也不等於功能都能用。
